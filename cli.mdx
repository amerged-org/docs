## Install and sign in

<InstallClients />

Run `ohmyhost login --json` and open the returned sign-in URL. The link already carries its confirmation code, so you do not type one. Sign in there, or create your account on that same page if you do not have one yet; signing up is open. Use the organizations returned by `whoami`; when several are available, select the one for this project. If none exists, create one through the get-started Skill.

## Authenticate

The CLI accepts two credentials and picks in this order:

1. `OHMYHOST_TOKEN` — a user API token. Set it and the CLI works immediately. No browser, no login.
2. The session saved by `ohmyhost login` — used only when `OHMYHOST_TOKEN` is unset.

`OHMYHOST_TOKEN` wins whenever it is set; the saved session is not read at all. If the value is not a valid `sk_…` token the command fails with `invalid_environment_token` and does not fall back.

These commands need the interactive login and refuse a token: `login`, `logout`, `organization create|list|use`, and `token create|list|revoke`. Run those in a process without `OHMYHOST_TOKEN`; preserve the existing private token file. Other commands use the token's current permissions and workspace role.

## Inspect and select a project

Run inside the repository:

```sh
ohmyhost init --dry-run --json
ohmyhost project list --json
```

Resolve actual blockers. Reuse an existing project, or create one after choosing isolated or shared data and setting `HOSTING_REGION` to the chosen `us` or `eu`:

```sh
ohmyhost project create --organization "$ORGANIZATION_ID" --name "My app" --data-mode isolated --region "$HOSTING_REGION" --idempotency-key "$PROJECT_REQUEST_KEY" --json
ohmyhost operation get "$PROJECT_OPERATION_ID" --json
ohmyhost project list --json
```

`ORGANIZATION_ID` comes from `whoami`. Create a unique `PROJECT_REQUEST_KEY` once and retain it for retries. `PROJECT_OPERATION_ID` is the creation response's `operation.id`. After success, select the created project's ID from the list as `PROJECT_ID`.

## Connect and deploy

Read the workspace's GitHub connection first. If it is not connected, an Owner or Admin runs connect:

```sh
ohmyhost github status --organization "$ORGANIZATION_ID" --json
ohmyhost github connect --organization "$ORGANIZATION_ID" --idempotency-key "$GITHUB_CONNECT_KEY" --json
```

Open its single `authorization.authorization_url`, then repeat the same connect request/key after browser confirmation until status is `connected`. This link handles installation/user authorization when needed. A failed or expired attempt needs the reported `last_failure` resolved and a new connect key for the same workspace.

Set `GITHUB_OWNER` and `GITHUB_REPOSITORY` to a repository covered by that installation. Retain one unique `SOURCE_REQUEST_KEY` for this source link:

```sh
ohmyhost link --project "$PROJECT_ID" --repository-owner "$GITHUB_OWNER" --repository-name "$GITHUB_REPOSITORY" --idempotency-key "$SOURCE_REQUEST_KEY" --json
```

Observe the returned source-link operation; it needs no second browser authorization for a covered repository. Missing access is repaired through `github.connection.settings_url` returned by GitHub status, then the same link command/key. No build starts until you deploy a plan.

Use the full SHA of the pushed commit as `COMMIT_SHA`:

```sh
ohmyhost plan --project "$PROJECT_ID" --commit "$COMMIT_SHA" --json
```

Read the plan, its requirements and credit effects. Set application [runtime secrets](/secrets) if required. Take `PLAN_ID` from `plan.id`, retain a new `DEPLOY_REQUEST_KEY`, and execute the approved plan:

```sh
ohmyhost deploy --project "$PROJECT_ID" --plan-id "$PLAN_ID" --idempotency-key "$DEPLOY_REQUEST_KEY" --yes --wait --json
```

## Verify progress and the application

```sh
ohmyhost operation get "$OPERATION_ID" --json
ohmyhost project status --project "$PROJECT_ID" --json
ohmyhost project dev-access create --project "$PROJECT_ID" --json
```

`OPERATION_ID` is the deploy response's `operation.id`. A wait timeout leaves the accepted operation running; inspect it without submitting another deployment. Follow returned polling guidance. Open the private `redeem_url` once, then test the clean Dev URL; keep access links out of logs and project notes.

## Common follow-ups

```sh
ohmyhost project context --project "$PROJECT_ID" --json
ohmyhost project handle check --handle quiet-otter-waves --json
ohmyhost credits account --organization "$ORGANIZATION_ID" --json
ohmyhost budget get --project "$PROJECT_ID" --json
```

For later automation, create a token from Profile → API Tokens or the [token commands](/login-tokens). New tokens stay valid until revoked. [MCP setup](/agents/mcp) uses the same account access.
