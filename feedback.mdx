---
title: "Report a bug or request a feature"
description: "Give the service a useful redacted report from your customer agent."
---

```sh
ohmyhost feedback submit --organization "$ORGANIZATION_ID" --kind issue --title "Deployment cannot continue" --description "$REDACTED_DESCRIPTION" --project "$PROJECT_ID" --operation "$OPERATION_ID" --error-code "$ERROR_CODE" --idempotency-key "$FEEDBACK_KEY" --json
```

Choose `bug`, `issue` or `feature_request`. Describe what you expected, what happened and the smallest reproduction. Project, environment and operation references must belong to the supplied organization. Omit optional references that do not apply.

MCP `feedback_submit` uses the same endpoint. Its schema identifies valid argument names. Use compact error/client-version identifiers without spaces, such as `cli/0.1.0`.

Keep the returned feedback ID and submission time. Replay an uncertain request with the same content and key; changed content gets a new key. A receipt confirms storage, not a promised fix date.

Do not submit tokens, passwords, signed links, raw environment files or customer records. If submission itself fails, return the failure honestly and continue independent work where possible.
